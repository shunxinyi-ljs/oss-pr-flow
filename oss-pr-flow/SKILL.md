# 开源 PR 贡献全流程

references/ 按需加载：quota.md（闸门一名额与选序）、discovery.md（闸门一三源侦察方法与深度使用手段）、checks.md（闸门四核查清单）、review.md（review 回应规程）、platform.md（命令、平台差异、仓库约定文件名）、templates/（输出格式）。用到才读，不预加载。

## 证据四件套（全文共用）

任一候选、任一修复都必须同时给出四件，缺一件不得进入下一闸门：

1. **现象**：可搜索的原始报错或行为描述；
2. **复现路径**：最小步骤或命令；
3. **定位**：能指到具体实现位置；
4. **可钉住的测试**：能在基线上失败、修复后通过。

## 入口分流

- **全流程**：用户要给某开源仓库提 PR，从闸门一开始，逐闸门推进，不满足通过条件就停下报告，不带病进入下一闸门。
- **只审查**：用户给出已存在的 PR 编号或正文草稿，直接进闸门四。调用前需同时满足：改动已可见、验证已跑过且有输出、草稿正文已写出；缺任一条就索取，缺证据不许开始审。
- **不适用**：纯代码审查；与提交无关的文案润色；用户还在排查阶段且没有要求接管全流程。

## 硬规则（违反即失败）

1. **禁止新增事实**。任何版本号、环境、性能数字、测试结论、影响范围，没有证据就不得写进正文。
2. **证据优先于文采**。每句陈述都要能指回改动内容、命令输出或仓库文件。
3. **不确定就停下**。无法核实的断言不得改写成更肯定的说法，只能降级为推测或列入待确认。
4. **降级前必须取证**。判为"推断/无据"之前必须先做至少一次检索或读取。"我没看过"不等于"没有证据"。
5. **不删用户价值陈述**。用户可见行为的变化、错误信息或提示文案、修复后用户该做什么——只能标"待核实"进待确认清单，不得直接删。
6. **并行规则：分支隔离、改动不重叠、同一缺陷只开一个 PR**。允许多个 PR 并行（各开独立分支、从最新主干拉出、独立走完五道闸门），但并行候选的预期改动文件不得重叠，同一缺陷不得开第二个 PR。各 PR 不共享证据、不复用彼此的审查结论。
7. **写操作需确认**。不擅自推送、不擅自创建 PR。允许的写操作只有两类：闸门五里经用户确认后的推送分支 + 创建草稿态 PR；反向验证中经用户确认的基线回滚（结束后必须恢复，确认工作区与开始时一致）。

## 闸门一·选题

**先算名额，再侦察**：开工前确认可用名额与上限（判据见 `references/quota.md`），按价值排序一次排满候选，避免窗口期空转。名额已满时只允许从已有候选里挑价值最高的一个继续推进，其余搁置，并停止侦察——配额满时继续找新候选是无效工作。

**来源（三条同等重要，不分先后、不降权，每次都要侦察；方法见 `references/discovery.md`）**：

- 他人问题：筛易上手、缺陷、求帮助类标记，读正文判断可复现性与改动规模。
- 源码缺陷：读核心实现、接口契约与异常分支，找能指到具体实现位置的缺陷。
- 深度使用：像真实用户一样把项目跑起来用一遍（CLI、示例、SDK、服务端；UI 类要真的操作界面），记录报错、卡壳、与文档不一致处，或提出有依据的新功能；能跑起来就不许只靠读代码声称"体验过"。

环境支持并行任务时可各来源并行侦察；侦察只找候选，不做修复、不联系维护者、不在仓库留任何痕迹。允许零产出：找不到就如实报"无候选"，禁止为了交差硬凑。

**复用他人问题前的四项核查**（任一命中即换候选，不抢）：

1. 是否已存在关联的开放 PR；
2. 是否已有指派人；
3. 评论区是否已有人认领；
4. 最近更新时间是否仍活跃。

**复用前必须在目标主线验证问题是否仍存在**：读实现、跑最小复现或查相关测试。已修复的判为失效候选——不写代码、不占名额，报告中注明"已在主线修复，原单待关闭"。**未核实不得进入闸门二**：改一个已不存在的问题会在公开仓库留下错误 PR，比不开更伤。此条同样适用于自己几天前记下的旧候选。

**撞车复核两个时点**：动手前一次，推送前再一次；后者不可省。

**候选成立门槛**：

- 现象可复现，且给出发生频率（N 次采样中 M 次，或说明每次必现）；仅"见过一次"不成立。
- 预期改动可控：参考上限 200 行，只计生产代码，测试行数单独统计、不计入。
- 非产品方向、路线争议、大规模重构类；无重复。
- 源码缺陷与深度使用得到的候选另需能指到具体实现位置，深度使用类还需给出可复现的操作步骤。

**汇总与筛选**（主流程做，不下放给子任务）：候选去重，并再查一次是否已有同问题的开放或已合并 PR；三条来源的候选统一按影响面、被驳回风险、证据强度排序，不因来源不同加权或降权；本次运行只选一个进入后续流程，要并行推进多个候选时每个另起独立会话、各开独立分支（硬规则 6）。无候选即如实结束，不进入闸门二。

**交付形态**：

- 自行发现的问题：问题描述与交付物同批发出；交付物发不出去时两者都不发（问题单一公开，任何人都可以直接引用它抢走实现）。例外仅限仓库模板强制要求或维护者明确要求。
- 修复他人已有问题：不新建问题单，正文以关闭关键字引用原单；只回应部分诉求时改用引用关键字并说明剩余范围。

条件满足后直接进入闸门二动手修复，不等任何人确认。选题结论照常输出：目标、为什么值得做、预期改动范围、落选候选清单（含搁置原因）。

## 闸门二·修复

- **先排除"设计如此"**：查代码注释、接口契约或文档、相关测试是否已经表达该行为；已表达的按设计处理，不提为缺陷。
- **先复现再动手**：修复前必须有失败证据（复现命令及输出），没有就不许改代码。
- **反向验证写死方法**：把修复涉及的生产文件从基线版本取回，跑新增测试确认失败，再恢复。**禁用暂存回退、禁用注释掉测试**——前者只退未提交改动、修复仍留在当前提交里，后者退不干净，两者都产生假绿。
- **测试替身真实性核实**：靠替身对象或手动制造异常构造的失败路径，必须逐行确认真实运行时会走到这条调用链（真实依赖在该场景下的行为是什么）。测的是测试自己构造的用例不计入证据。
- **条件跳过规则**：新增用例带环境依赖导致的跳过标记时，必须说明缺少依赖的环境里该路径如何仍被覆盖；做不到就改成强制走目标分支的桩，不许留下在多数环境形同不存在的用例。
- **区分两类测试用例**：反向验证后，把新增用例分成"在基线上失败"（修复验证，计入证据）和"在基线上仍通过"（护栏用例，不计入修复证据）。正文里笼统写"新增 N 个用例全部通过"会让维护者误以为都是修复验证，必须拆开说明。
- **屏蔽环境噪音**：本地私有配置导致的失败单独标注为环境副作用，不得进入补丁。
- **并行修复共享依赖环境**：不各自安装依赖，避免争用与锁等待。
- **diff 纪律**：不夹带格式化、依赖锁定文件变更、无关重命名或重构；沿用仓库现有代码风格；不改动流水线、静态检查等仓库配置。
- 通过条件：修复后复现命令通过；相关测试套件通过；每个改动文件都能说清为什么出现。

## 闸门三·成稿

- 按仓库约定起草：贡献指南与交付物模板的查找顺序见 `references/platform.md`，命中即停。
- 有模板严格按模板章节起草；无模板用最小集：一句话结论 → 改动内容 → 验证方式 → 风险/破坏性变更 → 关联问题。
- 标题含可搜索标识（错误码、函数名、模块名、场景），不写"修复了一个问题"。
- 初稿只写有证据的内容，拿不准的留白，交给闸门四处理，不许用推测填满。

## 闸门四·审查（独立取证）

**先忘掉你是作者。** 以下所有断言重新从改动内容、命令输出、仓库文件取证，不沿用成稿阶段的结论。

**1. 断言拆解**

触发词：中文（导致、崩溃、报错、失败、修复、解决、只影响、不影响、兼容、默认、首次、全部、唯一、性能、无破坏性变更、已测试）；英文等价（causes、crash、throws、fails、fixes、resolves、only affects、compatible、by default、all、every、only、performance、no breaking changes、tested、verified、never、always）。元规则：任何含数字的比较或版本号断言一律算。

| 级别 | 含义 | 能否写进正文 |
|---|---|---|
| E1 | 改动内容、命令输出直接支持 | 可以 |
| E2 | 仓库代码、文档、已合并 PR 间接支持 | 可以，措辞留余地 |
| E3 | 只能从会话推理得出 | 不可以，降级为"推测/待验证" |
| E0 | 原文有、但取证后仍找不到依据 | 删除或提问 |

内部维护清单：`断言 | 位置 | 证据 | 级别 | 处理`。最终报告只给结论，不铺整张表。

**2. 专项核查**（完整清单加载 `references/checks.md`）

- 问题真实性：复现步骤与会话内的复现记录一致；现象具体到可搜索（错误信息原文、触发条件、版本）；期望与实际成对出现；发生频率已如实给出。
- 修复针对性：改动触及正文声称的根因位置；测试覆盖改动分支；正文声明的范围与实际改动文件集合一致。
- 破坏性变更：逐项检查公开 API、默认值、配置键名、命令行参数或输出、序列化格式、错误码、权限行为。涉及就必须写进正文；不涉及才允许写"无破坏性变更"。同时扫描敏感信息：密钥、token、内部域名、绝对路径、邮箱。
- **设计缺口三问**（"有证据但考虑不全"是 review 被打回的主因，逐问作答，展开方法见 checks.md）：
  1. 边界值：空、单字符、超长输入都测过吗？
  2. 异常分类：不同故障是否被归进同一分支，导致调用方无法区分？
  3. 契约位置：语义变化是否写在接口契约上（含下游消费方与可观测性），还是只改了实现？
- 诉求回应：若关联了问题单，逐条核对其每个期望是否被回应；完全回应用关闭关键字，部分回应改用引用关键字并说明剩余范围。

**3. 做减法**

按顺序删：过程噪声（调试过程、失败尝试、中途结论）→ 空话（全面、优雅、显著提升、彻底解决）→ 逐文件改动复述（需要指路时只给"重点看 2-3 处 + 为什么"）→ 过度承诺 → 指责性表述 → 维护者自己能看出的冗余背景。禁区：用户价值陈述不删，按硬规则 5 处理。

长度预算：PR 正文 ≤ 400 词（中文约 800 字），模板必填字段不受约束。

**4. 输出**：固定四段（终稿 / 待确认清单 / 改动摘要 / 提交命令），格式加载 `references/templates/audit-output.md`。终稿不得出现 `[TODO]`、`<!-- -->`、"待补充"这类内容。用户改完要求重审时，只报仍未解决项和剩余待确认项，不整篇重出。

## 闸门五·提交

唯一路径：展示终稿和待确认清单 → 用户逐条处理完"必须补"项 → 用户明确同意 → 一次性执行推送分支 + 创建草稿态 PR。

- **推送前两件复核**：撞车复核第二个时点（见闸门一）；凭据覆盖分支内全部改动范围（含流水线配置类文件）。不覆盖就先补齐授权，不要反复重试。
- **与其他在途改动触达同一文件时**，同步主干必须保留双方逻辑，禁止整份取一侧；解决后两侧行为各需一条测试覆盖。
- **不可评审状态只是中转**：转正式状态才进入评审；不靠重复推送换取检查通过（重复推送会重置审批）。
- 只建草稿态，不建正式 PR。确认信息里必须完整列出将要执行的命令。
- 交付物因配额、权限或冲突创建失败时，不得改为单独发问题单（见闸门一交付形态）；报告原因并停下。
- 提交后输出链接。

**review 回应**：先读状态语义——意见态不等于否决，请求修改态才是卡住；派生仓库首次贡献者流水线显示的待批准是等维护者放行，不是失败。一次汇总回应：区分阻塞与非阻塞，全部处理完再推一次。完整规程加载 `references/review.md`。

## 通过标准

- 名额已先算后选，选序依据是影响面/被驳回风险/证据强度，不是"哪个容易写"。
- 三条来源（他人未关闭 issue / 源码缺陷 / 深度使用）都已侦察；某条确实无法执行时已说明原因（如项目无可运行入口），候选排序不因来源加权。
- 每个闸门的通过条件都满足，无跳步；复用的既有问题已在目标主线核实仍存在；撞车复核两个时点都做过。
- 交付形态正确：自行发现的问题单与交付物同批发出；承接他人问题不新建问题单。
- 反向验证用文件级回滚完成，mock 构造的失败路径已核实调用链，带跳过标记的用例已说明覆盖方式或已改造。
- 终稿每句陈述有据，或已降级为推测/待确认；每条被降级的断言能说清取证动作。
- 设计缺口三问逐问有答案；涉及错误码/状态值/默认值时已列出下游引用并逐条确认；路径可达性已确认。
- 待确认清单每条用户都能直接判断"补还是不补"。
- 未经用户确认未执行任何写操作。

## 维护纪律

- 主干只定义流程：五道闸门的顺序、每闸通过硬条件、证据四件套；注意事项与细节一律进 references。
- 主干不设行数上限，但也不能臃肿：判断标准是"这条内容是否每次都要对照"。只在特定场景才用得上的注意事项、命令、示例、清单，一律挪进 references，由主干按闸门指过去；单次运行要加载很多 references 才能跑完，说明分工错了，应合并精简，而非继续追加。
- 主干与 references 的流程语义变更必须同步 README。
