# 开源 PR 贡献全流程

references/ 按需加载：quota.md（闸门一名额判据）、checks.md（闸门四核查清单）、review.md（review 回应规程）、templates/（输出格式）。用到才读，不预加载。

## 入口分流

- **全流程**：用户要给某开源仓库提 PR，从闸门一开始，逐闸门推进，不满足通过条件就停下报告，不带病进入下一闸门。
- **只审查**：用户给出已存在的 PR 编号或正文草稿，直接进闸门四。调用前需同时满足：改动已在 git 可见、验证已跑过且有输出、草稿正文已写出；缺任一条就索取，缺证据不许开始审。
- **不适用**：纯代码审查；与提交无关的文案润色；用户还在排查阶段且没有要求接管全流程。

## 硬规则（违反即失败）

1. **禁止新增事实**。任何版本号、环境、性能数字、测试结论、影响范围，没有证据就不得写进正文。
2. **证据优先于文采**。每句陈述都要能指回 diff、命令输出或仓库文件。
3. **不确定就停下**。无法核实的断言不得改写成更肯定的说法，只能降级为推测或列入待确认。
4. **降级前必须取证**。判为"推断/无据"之前必须先做至少一次检索或读取。"我没看过"不等于"没有证据"。
5. **不删用户价值陈述**。用户可见行为的变化、错误信息或提示文案、修复后用户该做什么——只能标"待核实"进待确认清单，不得直接删。
6. **并行规则：分支隔离、改动不重叠、同一缺陷只开一个 PR**。允许多个 PR 并行（各开独立分支、从最新主干拉出、独立走完五道闸门），但并行候选的预期改动文件不得重叠，同一缺陷不得开第二个 PR。各 PR 不共享证据、不复用彼此的审查结论。
7. **写操作需确认**。不擅自推送、不擅自创建 PR。允许的写操作只有两类：闸门五里经用户确认后的推送分支 + 创建 draft PR；反向验证中经用户确认的基线回滚（结束后必须恢复，用 `git status --short` 确认与开始时一致）。

## 闸门一·选题

**先判名额，再侦察**：加载 `references/quota.md`，按其判据确定自己还能开几个 PR。名额已满时只允许从候选中挑价值最高的一个继续，其余搁置，并停止侦察——配额满时继续找新候选是无效工作。

**并行侦察**：环境支持子 agent / 并行任务时，同时派三个侦察任务，每个负责一个来源；不支持则串行。侦察任务只负责找候选，不做修复、不联系维护者、不在仓库留任何痕迹。

三个来源：

1. **现有 issue**：`gh issue list` 筛 `good first issue`、`bug`、`help wanted`，读正文判断可复现性和改动规模。
2. **源码阅读**：读核心模块找缺陷（错误处理缺失、边界条件、资源泄漏等），候选必须能写出复现路径。
3. **深度使用**：实际跑项目的典型流程，记录报错、卡壳、文档与行为不一致之处。

侦察纪律：

- **允许零产出**。找不到就如实报"无候选"，禁止为了交差硬凑。
- 每个候选附：问题描述、复现路径或测试缺口、预期改动规模（生产代码行数）、证据位置（issue 链接或 `文件:行号`）。

**汇总与筛选**（主流程做，不下放给子任务）：

- 候选去重，再 `gh issue list --search` / `gh pr list --search` 查重。
- 按 quota.md 的选序依据（影响面、被驳回风险、证据强度）排序，本次运行只选一个进入后续流程。要并行推进多个候选时，每个另起独立会话、各开独立分支（硬规则 6）。
- 三个来源都无候选 → 如实告知"本轮没找到合适的"，结束。这是合法结局，不进入闸门二。

选定候选的通过条件：

- 预期改动可控：参考上限 200 行**只计生产代码**，测试行数单独统计、不计入上限。
- 有明确的复现路径或测试缺口，不是"感觉可以更好"。
- 无重复；非产品方向、路线争议、大规模重构类。
- **无撞车**：动手前 `gh issue view <n>` 确认该 issue 最近无人留言认领、无 open PR 关联；已有别人在做的就换候选，不抢。

**issue 与 PR 原子化**：自己新发现的问题不在选题阶段先开 issue——issue 一旦公开，任何人都可以直接开 PR 引用它抢走实现。issue 必须与 PR 在同一次运行内一起发出；PR 因配额、权限或冲突发不出去时，issue 也不单独发。例外仅限仓库模板强制要求或维护者明确要求。

条件满足后直接进入闸门二动手修复，不等任何人确认。选题结论照常输出：目标、为什么值得做、预期改动范围、落选候选清单（含搁置原因）。

## 闸门二·修复

- **先复现再动手**：修复前必须有失败证据（复现命令及输出），没有就不许改代码。
- **反向验证写死方法**：把修复涉及的生产文件 checkout 到基线版本（`git checkout <基线commit> -- <生产文件>`），跑新增测试确认失败，再恢复。**禁用 stash、禁用注释法**——stash 只退未提交改动、修复仍在 HEAD，注释法退不干净，两者都产生假绿。
- **mock 真实性核实**：靠 mock / 手动 reject 制造的失败路径，必须逐行确认真实运行时会走到这条调用链（真实依赖在该场景下的行为是什么）。测的是测试自己的用例不计入证据。
- **skipif 规则**：新增用例带 `skipif` 时，必须说明缺少依赖的环境中该路径如何仍被覆盖；做不到就改成 monkeypatch 强制走目标分支，不许留下在多数环境形同不存在的用例。
- **区分两类测试用例**：反向验证后，把新增用例分成"在基线上失败"（修复验证，计入证据）和"在基线上仍通过"（护栏用例，不计入修复证据）。正文里笼统写"新增 N 个用例全部通过"会让维护者误以为 N 个都是修复验证，必须拆开说明。
- **diff 纪律**：不夹带格式化、lock 文件变更、无关重命名或重构；沿用仓库现有代码风格；不改动构建、CI、lint 等仓库配置文件。
- 通过条件：修复后复现命令通过；相关测试套件通过；`git diff --stat` 里每个文件都能说清为什么出现。

## 闸门三·成稿

- 按顺序找仓库约定，命中即停：`CONTRIBUTING.md` → `.github/CONTRIBUTING.md` → `docs/CONTRIBUTING.md` → `.github/PULL_REQUEST_TEMPLATE.md` → `.github/pull_request_template.md`。
- 有模板严格按模板章节起草；无模板用最小集：一句话结论 → 改动内容 → 验证方式 → 风险/破坏性变更 → 关联 issue。
- 标题含可搜索标识（错误码、函数名、模块名、场景），不写"修复了一个问题"。
- 初稿只写有证据的内容，拿不准的留白，交给闸门四处理，不许用推测填满。

## 闸门四·审查（独立取证）

**先忘掉你是作者。** 以下所有断言重新从 diff、命令输出、仓库文件取证，不沿用成稿阶段的结论。

**1. 断言拆解**

触发词：中文（导致、崩溃、报错、失败、修复、解决、只影响、不影响、兼容、默认、首次、全部、唯一、性能、无破坏性变更、已测试）；英文等价（causes、crash、throws、fails、fixes、resolves、only affects、compatible、by default、all、every、only、performance、no breaking changes、tested、verified、never、always）。元规则：任何含数字的比较或版本号断言一律算。

| 级别 | 含义 | 能否写进正文 |
|---|---|---|
| E1 | diff、命令输出直接支持 | 可以 |
| E2 | 仓库代码、文档、已合并 PR 间接支持 | 可以，措辞留余地 |
| E3 | 只能从会话推理得出 | 不可以，降级为"推测/待验证" |
| E0 | 原文有、但取证后仍找不到依据 | 删除或提问 |

内部维护清单：`断言 | 位置 | 证据 | 级别 | 处理`。最终报告只给结论，不铺整张表。

**2. 专项核查**（完整清单加载 `references/checks.md`）

- 问题真实性：复现步骤与会话内的复现记录一致；现象具体到可搜索（错误信息原文、触发条件、版本）；期望与实际成对出现。
- 修复针对性：diff 触及正文声称的根因位置；测试覆盖改动分支；正文声明的范围与 `git diff --name-only` 一致。
- 破坏性变更：逐项检查公开 API、默认值、配置键名、CLI 参数或输出、序列化格式、错误码、权限行为。涉及就必须写进正文；不涉及才允许写"无破坏性变更"。同时扫描敏感信息：密钥、token、内部域名、绝对路径、邮箱。
- **设计缺口三问**（"有证据但考虑不全"是 review 被打回的主因，逐问作答，展开方法见 checks.md）：
  1. 边界值：空、单字符、超长输入都测过吗？
  2. 异常分类：不同故障是否被归进同一分支，导致调用方无法区分？
  3. 契约位置：语义变化是否写在接口契约上（含下游消费方与可观测性），还是只改了实现？
- 诉求回应：若关联了 issue，逐条核对 issue 的每个期望是否被回应；完全回应用 `Fixes #<n>` / `Closes #<n>`，部分回应改用 `Refs #<n>` 并说明剩余范围。

**3. 做减法**

按顺序删：过程噪声（调试过程、失败尝试、中途结论）→ 空话（全面、优雅、显著提升、彻底解决）→ 逐文件 diff 复述（需要指路时只给"重点看 2-3 处 + 为什么"）→ 过度承诺 → 指责性表述 → 维护者自己能看出的冗余背景。禁区：用户价值陈述不删，按硬规则 5 处理。

长度预算：PR 正文 ≤ 400 词（中文约 800 字），模板必填字段不受约束。

**4. 输出**：固定四段（终稿 / 待确认清单 / 改动摘要 / 提交命令），格式加载 `references/templates/audit-output.md`。终稿不得出现 `[TODO]`、`<!-- -->`、"待补充"这类内容。用户改完要求重审时，只报仍未解决项和剩余待确认项，不整篇重出。

## 闸门五·提交

唯一路径：展示终稿和待确认清单 → 用户逐条处理完"必须补"项 → 用户明确同意 → 一次性执行推送分支 + `gh pr create --draft`。

- 只建 draft，不建正式 PR。转为 ready 由用户在 GitHub 上自己操作。
- 确认信息里必须完整列出将要执行的命令。
- PR 因配额、权限或冲突创建失败时，不得改为单独发 issue（见闸门一原子化规则）；报告原因并停下。
- 提交后输出 PR 链接。

**review 回应**（提交后收到 review 时）：先读状态语义——`COMMENTED` 不等于否决，`CHANGES_REQUESTED` 才是卡住；fork 首次贡献者的 CI 显示 `action_required` 是等维护者批准，不是失败，不要去拉失败日志。逐条回应、历史操作交代、flaky 对照等完整规程加载 `references/review.md`。

## 通过标准

- 名额判据已执行，选序依据是影响面/被驳回风险/证据强度，不是"哪个容易写"。
- 每个闸门的通过条件都满足，无跳步；issue 与 PR 同一次运行发出。
- 反向验证用基线 checkout 完成（非 stash/注释），mock 制造的失败路径已逐行核实调用链，skipif 用例已说明覆盖方式或已改造。
- 终稿每句陈述有据，或已降级为推测/待确认；每条被降级的断言能说清取证动作。
- 设计缺口三问逐问有答案；涉及错误码/状态值/默认值时已列出下游引用并逐条确认；路径可达性已确认。
- 待确认清单每条用户都能直接判断"补还是不补"。
- 未经用户确认未执行任何写操作。

## 维护纪律

- 主干行数膨胀、或单次运行需要加载三份以上 references 才能跑完，说明结构错了，应合并精简，而非继续追加。
- 主干与 references 的流程语义变更必须同步 README。
