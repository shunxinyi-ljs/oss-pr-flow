# 闸门一·三源侦察

三条来源**同等重要**：他人已提出但尚无对应 PR 的问题、源码级缺陷、深度使用体验。每次选题三条都要过一遍，不因来源不同加权或降权；某条确实跑不了（例如项目没有可运行入口）必须写明原因与卡在哪一步，不得静默跳过。

侦察前先按 `quota.md` 算清名额与在途上限；名额已满时停止侦察，只从既有候选里挑价值最高的一个。

三条来源产出的候选共用同一套门槛：现象可复现（给出频率）、复现路径、能指到实现位置、预期改动可控（生产代码参考上限 200 行）。第四个证据"可钉住的测试"在进入闸门二前补齐。

侦察阶段只找候选：不做修复、不联系维护者、不在目标仓库留任何痕迹。

## 一、他人已提出但尚无对应 PR 的问题

1. **捞候选**：`good first issue`、`bug`、`help wanted`、`P0`–`P3` 与模块标签；再用错误信息、函数名、模块名做关键词检索。
2. **读正文**：判断可复现性与改动规模；正文缺复现步骤的，自己在本地补一条最小复现。
3. **四项核查**（任一命中即换候选）：是否已有开放 PR、是否已有指派人、评论区是否已有人认领、最近是否仍活跃。
4. **主线核实**：读实现、跑最小复现或查相关测试，确认问题仍存在。已修复的判为失效候选，不写代码、不占名额。
5. **防"假开放"**：很多仓库用 `fix(...)` 提交直接修掉 issue 而不写 `Fixes #n`，issue 会一直开着。核对方法：查该 issue 涉及文件/类的近期合并提交与发布说明，或用症状关键词检索已合并 PR；也可以用 `linked:pr` 过滤与 `commenter:` 检索交叉验证。

## 二、源码级缺陷

从缺陷密度最高的地方入手，按类型定向阅读：

- **契约不一致**：Javadoc / 文档 / 接口注释声称的行为与实现不符（返回 null、抛错条件、边界语义）。
- **边界值**：空输入、单字符、超长输入、Unicode（代理对、组合字符、RTL）、越界索引、负数与溢出。
- **异常路径**：吞异常后仍返回成功、不同故障被归进同一分支、错误信息丢上下文、重试策略吞掉不可重试错误。
- **资源与生命周期**：未关闭的流/线程/连接、无界缓存与锁表、未清理的临时文件、泄漏的定时任务。
- **并发**：共享可变状态、检查与使用分离（TOCTOU）、顺序假设、锁粒度与死锁风险。
- **配置与默认值**：默认值改变行为却无文档、配置项被忽略、两处实现接受不同取值集合。

每个候选必须能指到 `file:line`，并写出最小复现或可失败测试；判定前先排除"设计如此"（注释、契约、测试是否已表达该行为）。

## 三、深度使用

把项目当成用户的日常工具真的用一遍，从摩擦点里找缺陷或有依据的新功能。**能跑起来就不许只靠读代码声称"体验过"**；跑不起来时如实说明卡在哪一步（缺凭据、缺依赖、环境不支持）。

按项目形态选手段，能用真实环境就不用 mock：

- **库 / SDK**：写一个最小消费者程序（独立目录、不入库），照 README 与文档走主要 API，记录报错、必须绕开的写法、与文档不符之处。
- **CLI**：装好跑主要子命令，覆盖帮助、正常路径、错误路径、管道与重定向、退出码。
- **服务端**：本地起服务，按文档做端到端调用（鉴权、核心接口、错误响应、并发请求），必要时用日志/抓包核对行为。
- **Web / UI**：用浏览器自动化（Playwright / Puppeteer / 浏览器 MCP 均可）真实操作：注册登录、主流程、空态、错误态、刷新与回退、多标签并发；截图留存作为现象证据。
- **长流程**：让一次真实任务跑完整（多轮对话、批量导入、断点续跑），观察状态持久化、恢复与清理。

体验记录必须写成可复现的步骤（环境、命令、输入、观察到的输出），不接受"感觉不好用"。提新功能时给出三件事：现状（现在怎么做、痛在哪）、期望（用户可见的变化）、最小验收方式；不得只写"建议支持 X"。

## 输出与取舍

侦察结束按来源分组列出候选，每条给出：来源、现象、复现路径、定位、预期改动规模、是否已有 PR/认领、落选原因。三条来源的候选合并去重后统一排序（影响面 / 被驳回风险 / 证据强度），不因来源加权。

无候选时如实报"无候选"，并说明三条来源各自侦察到什么程度；禁止为了交差硬凑。
