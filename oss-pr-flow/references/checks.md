# 闸门四专项核查清单

## 设计缺口三问（展开）

review 被打回的主因不是"没证据"，而是"有证据但考虑不全"。逐问作答：

**1. 边界值**：空值、单字符、超长输入、0/1/N 都测过吗？对每个边界问"这条路径有测试走到吗"，没有就补用例或在正文声明未覆盖。

**2. 异常分类**：不同故障是否被归进同一异常分支？分类错误会让调用方无法区分处理（例如把数据格式漂移和查询语法错误归为一类）。每种故障来源应能映射到独立的处理分支或独立的错误类型。

**3. 契约位置**：语义变化写在接口契约上（类型签名、公开文档、协议），还是只改了实现？契约没写，下游就不知道行为变了。这一问包含两个子项：

- **下游消费**：正文涉及错误码、状态值、默认值、API 字段这类被下游读取的值时，必须 grep 该值的所有引用，逐条确认下游能处理新取值（前端映射表、契约测试、文档、调用方）。陷阱：同一个值往往有多张映射表（一张管内联提示、一张管结果展示），只查一张会得出"下游没处理"的错误结论。
- **可观测性**：关键路径是否有足够信号；日志是否会重复打印（同一事件在多层各打一次）。

## 路径可达性

改动逻辑再对，所在路径被 feature flag、开关、环境变量、编译期常量关掉时，不能声称"修复了线上问题"。搜索开关确认改动路径当前是否执行：

- 可达（走默认路径）→ 可以写"修复了 X 问题"。
- 不可达 → 正文必须主动说明"当前不可达，为将来启用做准备"。这既诚实，也避免维护者认为作者不了解现状。
- 不确定 → 进待确认清单，不得默认可达。

## 破坏性变更与敏感信息（主干条目的展开）

破坏性变更逐项过：公开 API 签名、默认值、配置键名、CLI 参数或输出、序列化格式、错误码、权限或安全行为。涉及就必须写进正文；不涉及才允许写"无破坏性变更"。

敏感信息扫描：密钥、token、私钥、内部域名、绝对路径、邮箱、客户数据。发现即要求脱敏，并指出位置。
