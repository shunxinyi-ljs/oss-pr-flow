# review 回应规程（提交后收到 review 时使用）

## 状态语义（先读对，再动作）

- `COMMENTED`：意见，需要回应，不等于否决。
- `CHANGES_REQUESTED`：卡住，必须逐条解决或说服。
- `APPROVED`：通过。
- CI 显示 `action_required`：fork 首次贡献者的常态，等维护者批准运行，**不是失败**。不要去拉失败日志，不要当成红叉处理。

## 历史操作约束

- PR 存在未处理的行内 review 评论时，**不 rebase、不 force push**——会冲掉评论锚点，维护者无法再定位原评论对应的代码。需要同步主干时用 merge main。
- 已推送后改历史前，先确认没有未回应的行内评论。

## 回应格式

- 首行交代本次推送做了什么历史操作（merge main 还是 rebase，为什么），让维护者知道评论锚点是否还有效。
- 逐条对应：每条评论一条回应，说明"已改（哪个 commit）/ 不改（原因）"。不合并回应、不漏条。
- 改了代码的回应附上新证据（测试输出），只回复 "Fixed" 等于没回应。

## flaky 测试的处理

CI 出现疑似 flaky 的失败时：

- 必须带对照证据："该用例在干净基线上同样失败"，否则不得声称 flaky。
- 没有对照就老老实实排查，不许用"网络问题""环境问题"这类未查证的兜底说法——没跑过的环境、没验证过的能力，一律不写。
