# oss-pr-flow

## 这是什么

一个给 AI 编码助手用的**开源 PR 贡献全流程** skill。主干 `SKILL.md` 装每轮都要对照的规则，低频内容拆进 `references/` 按需加载。

从"找一个值得做的点"到"提交一个经得起 review 的草稿态 PR"，分成五道闸门，每道闸门不满足通过条件就停下，不带病进入下一步。

## 适用场景

- 需要给某个开源仓库贡献一个可复现、改动可控、不与在途工作重叠的修复；
- 手上已有一份 PR 草稿，需要逐条核对"说法有没有根据"；
- 不适用：纯代码审查、与提交无关的文案润色、仍在排查阶段且没有要求接管全流程。

## 流程概览

**选题 → 修复 → 成稿 → 审查 → 提交**

- **选题**：先算可用名额再侦察，按价值一次排满，避免窗口期空转。来源上三条同等重要、不分先后：他人已提出但尚无对应 PR 的问题、源码级缺陷（读到能指到实现位置的缺陷）、深度使用（真的把项目跑起来用一遍，UI 类项目要操作界面）；三条都要侦察，某条跑不起来要说明原因。三条来源的候选统一按影响面、被驳回风险、证据强度排序，不因来源加权。复用他人问题前做四项核查（是否已有开放 PR、是否已有指派人、评论区是否已有人认领、最近是否仍活跃），任一命中就换候选；并必须在目标当前主线核实问题是否仍存在，已修复的直接判为失效候选，不写代码、不占名额。成立门槛要求现象可复现并给出发生频率（N 次采样中 M 次，或说明每次必现）。撞车复核两个时点：动手前、推送前。
- **修复**：先排除"设计如此"（注释、契约或文档、相关测试是否已表达该行为），再复现出失败。反向验证用文件级回滚：把实现文件从基线取回，测试必须失败，禁用暂存回退与注释掉测试（两者都会产生假绿）。替身对象构造的失败路径要核实真实调用链；本地私有配置导致的失败单独标为环境副作用，不进补丁；并行修复共享依赖环境。
- **成稿**：按仓库贡献指南与模板章节起草，没有模板才用最小集；只写有证据的内容。
- **审查**：忘掉作者身份重新取证。每句断言按证据分级（E1 直接 / E2 间接 / E3 推断 / E0 无据），降级前必须先搜过；另有设计缺口三问（边界值、异常分类、契约位置）。产出终稿 + 待确认清单。
- **提交**：用户逐条确认后才推送分支并创建草稿态 PR。推送前复核撞车与凭据覆盖范围（含流水线配置类文件）；与其他在途改动触达同一文件时保留双方逻辑，两侧各需一条测试覆盖；不可评审状态只是中转，不靠重复推送换检查通过；review 回应一次汇总，区分阻塞与非阻塞。

## 交付形态

- 自行发现的问题：问题描述与交付物同批发出；交付物发不出去时两者都不发。
- 修复他人已有问题：不新建问题单，正文以关闭关键字引用原单；只回应部分诉求时改用引用关键字并说明剩余范围。

## 目录结构

```
oss-pr-flow/
├── SKILL.md                  主干：五闸门顺序、每闸通过硬条件、证据四件套
└── references/
    ├── quota.md              闸门一：名额判据与选序
    ├── discovery.md          闸门一：三源侦察方法（他人 issue / 源码缺陷 / 深度使用）
    ├── checks.md             闸门四：专项核查清单（设计缺口三问展开、路径可达性、破坏性变更）
    ├── review.md             收到 review 后的回应规程
    ├── platform.md           命令、平台差异、仓库约定文件查找顺序
    └── templates/
        └── audit-output.md   闸门四的固定四段输出格式
```

分工原则：主干只放闸门顺序、每闸通过硬条件、证据四件套（现象 / 复现路径 / 定位 / 可钉住的测试）；命令、模板、检查清单、语言或工具特定项一律进 `references/`。

## 安装与引用

把整个目录复制到你所使用的编码助手的 skill 目录下，目录名与 frontmatter 里的 `name` 保持一致；注意 `references/` 要一起复制，主干会在对应闸门按需加载。

## 使用

全流程：

```
用 oss-pr-flow 给 <owner/repo> 提个 PR
```

只审查（改动和草稿都已完成时）：

```
用 oss-pr-flow 审查这个 PR 的草稿
```

## 并行多个 PR

允许同一仓库并行推进多个 PR：每个候选另起独立会话、各开独立分支、从最新主干拉出、独立走完五道闸门。两个限制：改动文件不重叠（动手前对照在途分支复核文件集合）；同一缺陷只开一个 PR。

## 边界

- 不做代码 review，不判断方案好坏——只核对"说法有没有根据"。
- 未经确认不执行任何写操作：不推送、不建正式 PR、不改工作区。
